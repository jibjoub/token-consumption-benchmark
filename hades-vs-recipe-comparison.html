Does a bigger codebase break AI code comprehension?

A head-to-head read of the same "what's directly related to this object" query, run against a small ASP.NET app and a 28× larger COBOL mainframe — with and without the CAST Imaging MCP server.

Prepared for the NASA team · September 3, 2026 · Apps compared: Recipe (ASP.NET) vs. Hades (COBOL mainframe)
Scaling the codebase 28× did not cost any recall — both apps land in the same 98–100% range. What size clearly hurt was precision: on the small app, 47–81% of everything the model reported back was a false positive. On the mainframe, it was ~0%. Token usage does climb with size, as expected; dollar cost is muddier and needs more data before it's a clean story (see caveats).

The comparison

Both questions ask the same underlying thing — "what in this codebase directly touches object X?" — just aimed at a different kind of object. CAST Imaging's dependency graph doesn't distinguish a table from a subprogram: both are just nodes with direct edges, so the object type isn't a confound. What differs is scale, on both sides of the question: a much bigger codebase to search, and a much bigger ground-truth answer to find in full.

Hades · calls-to-immdates
"I'm planning to change the internal behavior of the subprogram IMMDATES (the number and types of parameters stay identical, only the logic changes). List all calls in the code that specifically invoke this subprogram — including calls made indirectly through a variable or field that holds the program name at runtime, not only literal CALL 'IMMDATES' statements. For each call, specify the file and whether the call is literal or made through a named field."
Ground truth: 244 calling programs — independently re-verified by Opus (see note below); only 11 use a literal CALL 'IMMDATES', the rest resolve through a copybook field or a locally-declared one.
Recipe · pages-directly-related-to-PrivateMessage-table
"I want to modify the PrivateMessage table. Count and list all the aspx pages that can be directly impacted by this change."
Ground truth: 8 aspx pages.
Ground-truth rigor: the Hades answer (244) wasn't taken on faith. It was first derived by one model reading the codebase, then independently re-derived from scratch by a second model (Opus) in a separate pass. The recheck found a genuine 5-caller gap (239 → 244) — a third call mechanism the first pass hadn't searched for — and zero false positives in the original list. That gives real confidence in the ~0% noise reading below: it isn't an artifact of an incomplete answer key.

What this says

1

Recall barely moves with size — precision is where size shows up

Both apps land in the same 98–100% recall band regardless of condition. The real gap is noise: Recipe's answers are 47–81% false positives on this question type, while Hades' are effectively clean (~0%) despite the codebase being 28× bigger and the answer set 30× larger. If anything, the bigger, more mechanically well-defined codebase produced more precise answers, not less.

2

Token usage scales with size; dollar cost doesn't (yet) tell a clean story

Hades uses more tokens than Recipe in every single condition (2.19M–4.47M vs. 1.46M–2.10M) — a consistent, monotonic size signal. Raw dollar cost is noisier: Hades actually costs less than Recipe in the without/with conditions despite using more tokens (cache efficiency), and both apps' with-forced numbers carry a caching caveat (see below). Token volume is the more trustworthy size signal in this dataset; cost needs cleaner data before drawing a size-vs-cost conclusion.

3

The MCP tool is used opportunistically, not automatically

Even when available, the model reached for the CAST Imaging tool only 53% of the time on Hades and 32% on Recipe. Explicitly forcing it (with-forced) pushes usage to 65% on Hades and 75% on Recipe — never 100%. The model still sometimes falls back to reading the code directly, even under instruction to use the MCP tool — and on Hades specifically, a deeper look found that's often because the MCP server simply wasn't reachable in that session (see the caveat below).

4

Precision, not correctness, is the strongest case for CAST Imaging so far

Recall was already high without any special tooling on both apps. The gap this data actually shows is in noise — how much junk rides along with a correct-ish answer. That's arguably the more expensive failure mode in practice: a developer has to manually filter 47–81% false positives out of Recipe's answers, versus essentially none out of Hades'.

Read this before presenting it as settled

Single question pair, modest n. This is one "directly related to X" question per app, 22–36 runs per condition. It's a real, consistent pattern — not yet a broad claim about all query types or all codebase sizes.
with-forced cost/tokens carry a caching caveat. A prompt-cache isolation bug (fixed 2026-09-03) let back-to-back with → with-forced calls silently inherit a warm cache, deflating cost. Hades' with-forced numbers blend pre- and post-fix runs; Recipe's data predates the fix entirely. Recall and noise are unaffected by this (caching doesn't change what the model reports) — only cost/token comparisons involving with-forced should be read as directional.
Hades' with-forced median accuracy hides a real problem. A separate deep-dive found that on 2026-09-01 the with-forced prompt was rewritten to forbid falling back to source code, and since then 41.7% of with-forced runs return a hard empty answer (recall 0%) whenever the MCP server happens to be unreachable that session — a failure mode that doesn't exist in the with condition (which can still fall back). Because more than half of with-forced runs still succeed, the median accuracy/noise numbers above look unaffected — they aren't measuring what you'd assume. See the separate hades-with-forced-prompt-change.html report for the full breakdown.
Ground truth for Hades was corrected mid-project. 239 → 244, via an independent second-model re-verification (see the callout above). No comparable independent recheck has been done yet for Recipe's 8-page answer or for Hades' other two questions with unverified ground truth (impact-ims-pcb-immmbrdb: 65, CAST-self-reported only; programs-directly-related-to-EMP-table: 58, no data collected yet).
