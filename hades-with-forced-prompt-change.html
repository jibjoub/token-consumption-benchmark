What actually changed

Commit b27e27a, "add a prefix and a suffix to force only the use of MCP server" — Sep 1, 2026, 16:31 (America/New_York), recorded in git under JB Despujol's account. It only touches the with-forced condition; without and with are untouched and serve as a control below.

Before
Suffix (appended after the question)
"You have access to CAST Imaging MCP tools for structural and transaction analysis of this codebase. Use them to answer this question rather than relying solely on reading the source code directly."
After
Prefix (new)
"Using only CAST Imaging MCP tools"
Suffix (rewritten)
"You have access to CAST Imaging MCP tools for structural and transaction analysis of this codebase. Rely solely on the CAST Imaging MCP server to answer this question — do not read the source code directly."
The change is a wording shift from "prefer MCP" to "MCP only, no fallback." Nothing else about the harness, the question, or the ground truth changed at the same time.

Root cause

1

The MCP server going missing mid-session isn't new

In the untouched with condition, the CAST Imaging tool is absent or unused in 14 of 30 runs (47%) across the whole dataset — a rate similar to what with-forced sees after the change (37.5% not used). This looks like a pre-existing MCP-connectivity flake (a session occasionally starting without the tool registered), not something the prompt rewrite introduced.

2

The rewrite removed the only safety net for that flake

Under the old wording, a session that started without MCP could still read the COBOL source directly and produce a real (if less "MCP-verified") answer — that's exactly what happens in every one of those 14 with runs, landing at 232–245 out of 244 expected callers. Under the new wording, the same starting condition instead produces a flat refusal: 9 of 10 zero-recall rows explicitly cite "no CAST Imaging MCP tools available in this session" as the reason for not answering at all.

3

When MCP does connect, the new wording is not the problem

13 of the 14 non-empty with-forced runs after the change land at 99–100% recall — indistinguishable from before the change. The rewrite doesn't make the model worse at the task; it makes an already-existing infrastructure hiccup unrecoverable instead of invisible.

Read before trusting this

Only 2 with-forced runs exist from before the change — and there's a structural reason. Git history shows calls-to-immdates was only added to the shared question file at 15:08 on Sep 1 (commit 73af55c); the prompt was hardened just 83 minutes later at 16:31 (b27e27a). There was barely a window for a "before" sample to exist at all — this isn't data lost to the cleanup (confirmed against the pre-dedup backup too, still 2). The one Aug 27 row predates even that commit and is most likely a local exploratory run folded into the Sep 1 "new results" commit before the question was formalized. A literal before/after comparison on with-forced alone is necessarily thin. The same-window with-forced vs with contrast above is doing the real evidentiary work here — same time period, same real-world MCP reliability, only the wording differs, and it's a much bigger sample (24 vs 27).
This is one question, one condition. Whether this same "instruction removes the fallback" pattern shows up on other Hades or Recipe questions, or in the with condition if it were ever similarly hardened, hasn't been checked.
results.jsonl had a data-hygiene bug, now fixed. While building this report, 35 exact-duplicate rows and 22 more stale junk rows (session-limit hits that predate the strip fix) were found and removed from results.jsonl, all within hades/calls-to-immdates. This report and the regenerated scores-hades.jsonl use the cleaned data (committed 118e6d2); anything computed from the file before that commit — including n-counts in the earlier Hades/Recipe comparison report — was inflated and should be treated as superseded.
Two secondary anomalies, not this report's focus. One run reports count 798 (a malformed single list entry, not real over-counting — recall/precision are actually fine). Another reports the correct count of 244 but only 18.4% true recall — a confidently-wrong case worth its own look separately from the zero-recall pattern documented here.

What to do about it

Two independent things surfaced here, and they call for different fixes. The MCP-connectivity flake (~40–50% of sessions start without the tool registered) is the deeper issue and is worth its own investigation — it's happening regardless of prompt wording. The prompt wording is a smaller, cheaper fix: either soften it back to "prefer MCP, fall back to source if it's unavailable" (loses some purity in what with-forced measures, but stops burning ~40% of runs on empty answers), or keep the hard requirement but treat a "no MCP tools available" refusal as a distinct, excluded diagnostic outcome rather than folding it into the same accuracy number as a real attempt.
